# 0008. Admin UI foundation — rationale

Decision record for [index.md](./index.md). Not read by `/develop`; read by humans and by `/architect` on update or supersede.

## Context

Slice 1 of the platform (features 2 through 8) is close to done; the deterministic workflow MVP ships via HTTP today. Slice 2 opens the admin UI, and this feature is the one that picks the stack for every later screen (feature 10's workflow configuration editor, feature 11's execution browser). The scope row's done when is three sentences long: boot locally, authenticate against the API with a dev key, render empty state screens for Workflows and Executions.

The context behind the decision:
- The backend is Python 3.12 / FastAPI / Postgres (spec 0001). It is pure JSON over HTTP, with Problem Details error envelopes (spec 0007), cursor pagination on list endpoints, and OpenAPI generated by FastAPI. No existing frontend code; this is a greenfield UI stack decision.
- The admin UI is operator only. No SEO, no public exposure, no multi tenant isolation now. Feature 26 adds real auth later; this spec is explicit about building a stub whose boundary Feature 26 can swap.
- The project default workflow is Skateboard: ship the thinnest usable whole first, then grow. That shapes the Build plan toward one real screen rather than many empty ones.
- The team is small; recruiting biases toward boring, proven choices with large ecosystems. "Boring is a feature" applies strongly: React, Vite, pnpm, Tailwind are each the largest in their lane.
- Feature 10 needs forms (workflow config, extraction rule editing). Feature 11 needs tables and detail panels. That shapes the UI library choice toward shadcn/ui (strongest template coverage) and React Hook Form (industry standard).
- `AGENTS.md` records a strong preference for one tool per job (ruff on the Python side). That carries into Biome (lint + format in one Rust binary) over ESLint + Prettier, and `openapi-typescript` + `openapi-fetch` (small, focused) over heavier SDK generators.

Not deciding would freeze Slice 2 entirely: features 10 and 11 both depend on a shell to live in.

## Options considered

The staged conversation worked three real forks: UI shape (SPA served separately vs HTMX on FastAPI vs SSR framework), framework (React vs Vue vs Svelte), and UI library (Tailwind + shadcn vs Mantine vs MUI vs headless). Everything else was single tool decisions where one choice clearly dominated.

### Option 1: React 19 SPA served separately (the chosen stack)

A standalone React 19 app under `frontend/`, bundled by Vite 8, consuming the FastAPI JSON API over `/api/v1`. See [index.md](./index.md) for the full stack walk.

**Pros**:
- Clean Python / Node boundary; backend stays a pure JSON API.
- Largest ecosystem for the specialized admin widgets Feature 10 and 11 need (JSON editors, dense tables, nested forms).
- Vite dev proxy and FastAPI StaticFiles mount give same origin in dev and prod, so there is no CORS.
- shadcn/ui copy in model keeps the primitives tunable in place.
- Full type safety through `openapi-typescript` plus TypeScript strict, matching the backend's mypy strict discipline.

**Cons**:
- Adds a Node toolchain and a second build.
- API key in `localStorage` is a known XSS exposure (acceptable as a stub, must not survive to production).
- TanStack Router is less common than React Router (community skill partially offsets).

### Option 2: Server rendered HTMX + Jinja2 inside FastAPI

FastAPI renders Jinja templates; HTMX handles partial swaps for interactivity. No Node toolchain, one build, one language.

**Pros**:
- Smallest surface area, fewest new skills.
- One deploy artifact, no dev proxy.
- Operators mostly need lists and forms, both of which HTMX handles reasonably.

**Cons**:
- Feature 10's workflow configuration editor (nested JSON, selector preview with live DOM inspection) and Feature 11's execution browser (long result bodies, timing drilldowns) are awkward in HTMX; the slope decays quickly into Alpine.js or Stimulus bolt ons.
- Loses typed API contract end to end.
- Server rendering a form validation error path tightly couples backend templates to frontend state in a way that is hard to evolve.

### Option 3: SSR framework (Next.js, Nuxt, SvelteKit) as a separate app

Full SSR framework in a sibling folder, consuming the FastAPI backend.

**Pros**:
- Rich ecosystem (same as Option 1 for React family).
- Great developer experience.

**Cons**:
- Adds a Node server to deploy in production, not just a Node build step. For an internal admin tool with no SEO this is pure cost.
- More framework to learn, bigger template coverage of concerns the admin UI will never use (streaming, server components, edge rendering).

## Rationale

Option 1 wins on three forces from Context taken together: Feature 10 and 11 need admin specific widgets that React has the deepest coverage for; the backend's "pure JSON over HTTP with Problem Details" contract (spec 0007) is best honored by a typed API client, which an SPA with `openapi-typescript` delivers end to end; and the operational cost of Option 3 (a Node server in production) buys nothing because the admin UI is internal, no SEO. Option 2 is attractive on day one but visibly decays by Feature 10 (nested JSON editing is the first HTMX cliff) and by Feature 11 (dense tables with filtering are a React Table story, not an HTMX one). Choosing Option 1 now costs a Node toolchain but keeps every later Slice 2 screen cheap.

Inside Option 1 the walk went: React 19 over Vue or Svelte (ecosystem for admin widgets, hiring pool); Tailwind 4 + shadcn/ui over Mantine or MUI (copy in primitives beat batteries included for a bespoke admin; MUI's Material look is hard to escape); TanStack Router over React Router (fully typed routes match the mypy strict ethos; the extra Agent Skill offsets the smaller community); TanStack Query (standard, no real alternative for REST SPAs); React Hook Form + Zod (industry standard; Zod mirrors Pydantic validation on the Python side); Biome 2 (one Rust binary, matches ruff pattern); Vitest + Playwright (Vite native, no Jest config churn); `openapi-typescript` + `openapi-fetch` (small, focused, matches "OpenAPI stays accurate" rule in `AGENTS.md`). Each pick cites a specific force from Context above.

The engineer's preference lined up with every recommended pick; no conflict to flag.

## Landscape scan evidence

The landscape scan the researcher subagent returned (cached at `docs/.agent-cache/research/admin-ui-landscape.md`) is the source of the versions and option labels above. It was asked to cover ten layers (framework, bundler, package manager, routing, server state, UI library, forms, lint, testing, TypeScript) in no more than five searches and eight page fetches. Key factual outputs that shaped the stack walk:

- React 19, Vue 3.5, Svelte 5 are all current major majors with strong momentum; React's component library coverage is materially deeper for admin specific widgets.
- Vite 8 is the de facto bundler across every candidate framework (Rolldown powered).
- pnpm 10 beats npm on install speed and strict hoisting; Bun 1.4 is fast but CI pin stability is still churny.
- TanStack Router 1.x is fully typed through search params; React Router 8 has weaker types and framework mode noise an SPA does not want.
- Tailwind 4 (Oxide engine, CSS first config) is a clear major over Tailwind 3; shadcn/ui is the dominant copy in primitives library.
- Biome 2 is now a credible single Rust binary for lint + format.
- TypeScript 7 (native Go port compiler) ships roughly a 10x faster compile; relevant for CI feedback on the frontend.

Nothing in the scan contradicted the recommended stack; the engineer picked every recommended option.
